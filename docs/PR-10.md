# PR-10 — Safe browser cleanup architecture

PR-10 replaces broad browser cleanup heuristics with profile-aware, risk-separated cleanup scopes.

The governing rules are:

1. **Regenerable cache may be Safe.**
2. **History is Review.**
3. **Cookies/sessions, saved credentials and persistent/offline site data are Sensitive.**
4. **The scanner must authorize only the exact files/directories it measured and displayed in the Cleanup Plan.**
5. **Purgio must not guess a destructive target when the browser owns the real path/state.**

## Profile discovery

### Chromium family

Chromium documents that each browser profile is a subdirectory of the user data directory. PR-10 discovers only conservative profile names:

- `Default`
- `Profile <digits>`

It does not automatically treat `System Profile`, `Guest Profile` or arbitrary directories as user profiles.

Opera is supported as a standalone Chromium-style profile root where appropriate. On Windows its profile root is resolved from `%APPDATA%\Opera Software\Opera Stable` instead of the previous incorrect `%LOCALAPPDATA%` assumption.

### Firefox

Firefox is no longer treated as though the `Profiles` directory itself were one profile. Purgio enumerates actual child profile directories and accepts only candidates containing known profile markers such as `prefs.js`, `places.sqlite`, `cookies.sqlite`, `sessionstore.jsonlz4` or `storage`.

Linux supports both the legacy Firefox root and the XDG configuration root, preferring the legacy root only when it actually exists.

### Safari

Safari remains conservative. PR-10 does not invent cache/session paths that are not present in the known Safari root. Existing `LocalStorage` is classified as Sensitive site data rather than Safe cache.

## Cache directories are platform-aware

Chromium explicitly separates the user cache directory from the profile directory on macOS and Linux:

- Windows: cache base is normally the profile directory.
- macOS: a profile under `~/Library/Application Support/...` maps to the corresponding `~/Library/Caches/...` path.
- Linux: a profile under the system config directory maps to the corresponding XDG cache directory.

PR-10 mirrors this behavior before looking for cache subdirectories.

Firefox also has a local profile/cache root distinct from the main profile root. Purgio maps a discovered Firefox profile name to the platform local profile root before scanning `cache2`:

- Windows: `%LOCALAPPDATA%\Mozilla\Firefox\Profiles\<profile>`
- macOS: `~/Library/Caches/Firefox/Profiles/<profile>`
- Linux: `${XDG_CACHE_HOME:-~/.cache}/mozilla/firefox/<profile>`

## Cache categories

Regenerable cache is split into separate Safe categories instead of one ambiguous bucket:

- HTTP cache (`Cache` for Chromium-family browsers, `cache2` for Firefox)
- Code Cache (Chromium family)
- GPU Cache (Chromium family)

Each category receives only existing paths that pass symlink/reparse/critical-path checks. Site storage is never included in these Safe cache categories.

## History — Review

History is authorized per exact profile file:

- Chromium family: `History`
- Firefox: `places.sqlite`
- Safari: `History.db` when present in the known root

History is Review because deletion affects user-visible navigation history and history-based suggestions.

## Cookies and session state — Sensitive

Cookies and session restoration data are separate from cache. Examples include:

- Chromium: `Network/Cookies`, `Cookies`, `Sessions`, `Current Session`, `Current Tabs`
- Firefox: `cookies.sqlite`, `sessionstore.jsonlz4`, `sessionstore-backups`

These are Sensitive because deleting them can sign users out and remove restorable session state.

## Saved credentials — Sensitive

Saved credentials are a separate Sensitive category rather than being mixed into cookies/cache:

- Chromium: `Login Data`, `Login Data For Account`
- Firefox: `logins.json`, `key4.db`

Purgio explicitly warns that deleting these files can remove access to saved passwords.

## Persistent and offline site data — Sensitive

The previous implementation incorrectly treated broad Chromium `Default\File System` storage as an incomplete-download artifact and Safari `LocalStorage` as Safe cache.

PR-10 moves persistent/offline storage into a dedicated Sensitive category:

### Chromium family

- `Local Storage`
- `IndexedDB`
- `File System`
- `Service Worker`

### Firefox

- `webappsstore.sqlite`
- `storage`

### Safari

- `LocalStorage` when present under the known Safari root

These paths may contain web-app state, offline content and site data, so they are never selected as Safe cache.

## Incomplete downloads — intentionally not emitted

PR-10 removes the old incomplete-download category rather than pretending it can discover the real files from the browser profile.

Chromium creates `.crdownload` as an intermediate path alongside the actual download target. The download destination can be user-selected or configured. Firefox `.part` files likewise belong to download targets rather than a stable per-profile cache location.

Therefore Purgio does **not**:

- scan `Default\File System` as a substitute;
- assume all incomplete downloads live in the profile;
- recursively scan a guessed Downloads folder and label the result browser-specific.

A future implementation must resolve the browser-owned destination/state or expose a clearly bounded user-selected folder workflow before deleting resumable artifacts.

## Browser crash reports — Review

PR-10 adds a bounded Review category for browser crash artifacts, using known browser crash-report roots and exact file extensions only.

Chromium-family report roots follow Chromium's platform conventions (`Crashpad` on Windows/macOS, `Crash Reports` on Linux). Firefox uses its `Crash Reports` tree. Purgio enumerates only direct report files matching known crash-report extensions such as `.dmp`, `.meta`, `.txt` and `.extra`; it does not authorize entire browser roots.

Crash reports are Review because they may be needed to diagnose browser failures.

## Filesystem trust boundary

All browser candidates pass the same safety model used by the cleanup engine:

- `symlink_metadata`, not link-following metadata;
- critical-path filtering;
- reject direct symlinks/reparse points;
- reject Windows paths with reparse/junction ancestors;
- reject generic symlink/reparse ancestors before measuring or authorizing a path.

The scanner therefore avoids showing a benign-looking path that physically redirects into another tree.

## Windows diagnostic carry-over

PR-10 also closes one remaining PR-09 consistency gap: direct files inside `C:\Windows\Minidump` now receive the same reparse-ancestor check already used for application CrashDumps and `MEMORY.DMP`.

## Localization

New browser metadata is localized ES/EN. Dynamic translation rules put specific labels (HTTP Cache, Code Cache, GPU Cache, Crash Reports) before the generic `Caché de ...` rule to avoid ambiguous English output.
