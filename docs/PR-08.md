# PR-08 — Backend-verified Cleanup Plan

PR-08 turns cleanup into an explicit, reviewable flow:

**Analyze → Select → Verify plan → Execute → Review result**

The goal is transparency without weakening the trust boundary established in PR-01.

## Trust model

React is not a source of truth for destructive operations.

1. The UI sends only the selected cleanup IDs to `preview_clean_items`.
2. Rust resolves those IDs against the current backend-owned cleanup catalog.
3. The Cleanup Plan displays only the items, paths, estimated sizes, risk levels and impact returned by Rust.
4. The preview also returns a compact plan revision derived from the normalized IDs, authorized paths and risk levels the user reviewed.
5. When execution starts, the UI sends only the IDs and that revision to `clean_items`; it never sends paths as authorization.
6. Rust resolves the catalog again, recomputes the revision and refuses to delete anything if the scope changed after preview.

Unknown IDs still fail closed and duplicate IDs remain deduplicated by the backend resolver.

### Preview-to-execution consistency

Some cleanup targets are dynamic. A file can appear or disappear between the moment the user reviews a plan and the moment they press Execute.

The plan revision closes that transparency gap:

- identities are normalized by item ID;
- each item's path list is sorted and deduplicated;
- the risk level is part of the identity;
- byte size and display copy are intentionally excluded, because active caches can change size without changing cleanup scope;
- if IDs, authorized paths or risk change, execution returns `PLAN_CHANGED` before deletion and the UI discards the stale plan;
- the user must generate and review a fresh plan before retrying.

The revision is a consistency token, not an authorization primitive. The destructive authority remains entirely in the Rust-owned catalog and the safety validator.

## Mandatory Cleanup Plan

The Cleanup Plan is always shown before a destructive cleanup operation, including Safe items. Safe does not mean invisible.

The previous `confirm_delete` preference no longer allows bypassing this review step. Its meaning is narrowed to **reinforced risk confirmation**: when enabled and the verified plan includes Review or Sensitive items, the user must explicitly acknowledge that those risk items and their authorized paths were reviewed.

This preserves the existing persisted setting while removing the possibility of a configuration option disabling transparency.

## Structured execution result

`clean_items` no longer returns only a byte count. It returns a backend-authoritative run result containing:

- estimated bytes from the current authorized catalog;
- bytes actually freed;
- number of attempted, completed, partial, failed and no-op items;
- item-level status and actual bytes;
- path-level status, actual bytes and issues.

Statuses are serialized as:

- `completed`
- `partial`
- `failed`
- `no_op`

A mixed success/failure item is explicitly `partial`. If every path fails, the item is `failed`. A target that disappeared after preview becomes `no_op`; Purgio never broadens the target to compensate.

## Filesystem reporting

The cleaner now records safety skips and filesystem errors encountered during recursive cleanup instead of reducing every best-effort traversal to a single byte total.

Existing safeguards remain in force:

- critical paths are blocked;
- relative cleanup targets are rejected;
- root symlinks are rejected;
- Windows reparse points and junctions are never traversed;
- nested critical paths/reparse points remain skipped;
- canonical paths are rechecked before recursive deletion.

The result model only exposes outcomes. It does not authorize any additional path.

## UX

The verified plan shows:

- estimated recoverable space;
- selected item count;
- number of backend-authorized paths;
- Review/Sensitive count;
- localized name, impact and recommendation;
- risk label using text in addition to color;
- expandable exact authorized paths.

After execution, the same flow shows:

- actual bytes freed versus initial estimate;
- completed/partial/failed/no-op totals;
- per-item outcome;
- expandable path-level outcomes and issues.

A cleanup containing partial or failed items produces a warning result rather than a total-success message. A stale plan produces a separate warning explaining that Purgio deleted nothing and that a new preview is required.

## Double execution protection

Plan preparation and execution each have an in-flight guard. Cleaner and Browser cleanup controls are disabled while the backend preview is being prepared or a cleanup run is executing.

## Localization

All new user-facing plan and result copy is integrated into the ES/EN localization layer introduced in PR-07. Backend operational IDs, paths and authorization decisions stay language-independent.

## CI

PR-08 keeps the focal rustfmt gate on the changed cleanup/security/persistence modules. Directly formatting the crate root `lib.rs` with stable rustfmt traverses child modules and would introduce unrelated pre-existing formatting churn in `scanner.rs`, `startup.rs` and `system.rs`; therefore the `lib.rs` command-contract changes are validated through all Rust tests and strict crate-wide Clippy instead of weakening or globally expanding the formatting diff.

Required checks remain:

- production `npm audit`;
- i18n coverage and locale tests;
- TypeScript/Vite build;
- focal Rust formatting;
- all Rust tests, including plan revision and structured-outcome cases;
- strict Clippy with `-D warnings` across the crate;
- NSIS branding validation;
- real Windows NSIS installer build and `*-setup.exe` verification.

## Out of scope

PR-08 does not add cleanup targets or broaden existing paths. Windows cleanup expansion belongs to PR-09 and browser target hardening/expansion belongs to PR-10.
