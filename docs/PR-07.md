# PR-07 — Spanish/English localization and system locale detection

Purgio now separates the persisted language preference from the effective UI language.

## Language model

- `system`: follows the operating-system locale.
- `es`: explicit Spanish override.
- `en`: explicit English override.
- Spanish BCP-47 tags such as `es-GT` and `es_ES` resolve to Spanish.
- Unsupported or missing system locales fall back to English.
- Explicit user overrides always take precedence over the detected locale.

The persisted state schema is version 2. Existing v1 `es`/`en` values are preserved during migration because v1 did not record whether they represented a default or an explicit user choice.

## Tauri permissions

Purgio uses `@tauri-apps/plugin-os` / `tauri-plugin-os` only for locale detection. The main capability grants only `os:allow-locale`; no broad OS permission is enabled.

The stale frontend `@tauri-apps/plugin-opener` dependency was removed.

## Translation architecture

- `src/i18n-core.ts`: pure language resolution logic.
- `src/i18n.tsx`: translation dictionary, interpolation, React provider/context, and presentation-only translation of backend metadata.
- Operational cleanup IDs, paths, categories, risk levels and authorization remain independent from language.
- `src/utils/format.ts` uses `Intl.NumberFormat` and `Intl.RelativeTimeFormat` with `es-GT` / `en-US`.

Localized surfaces include sidebar, splash, title bar, dashboard, system cleaner, browser cleaner, startup applications, background processes, settings, update UI, confirmation dialogs and notifications.

Backend metadata shown by Cleaner, Browsers, Startup and Background is translated at the presentation layer as well, including Windows/macOS/Linux cleanup descriptions, developer caches, browser history/session/download metadata and common process descriptions/warnings. This translation layer never changes backend IDs, paths, registry keys, PIDs, risk levels or authorization decisions.

## CI

`scripts/check-i18n.mjs` is a permanent frontend gate. It:

1. fails when a literal `t('…')` key lacks an English translation;
2. validates seven locale-resolution cases, including Spanish/English system locales, unsupported locales, missing locale and explicit overrides.

The first localization run intentionally exposed missing English keys and they were added instead of weakening the gate. A later TypeScript build found three integration issues (missing translation import, unused type import and an unsupported `replaceAll` call); all were corrected without changing the TypeScript target.

The normal CI still requires production dependency audit, localization coverage, TypeScript/Vite build, Rust formatting/tests, strict Clippy, NSIS branding validation, real Windows installer build and final `*-setup.exe` verification.

## Compatibility

Changing language is a presentation concern only. It must never change cleanup targets, security decisions, startup registry identifiers, process IDs or updater trust behavior.
